# Requirements Document

## Introduction

Repo Graveyard needs a working project foundation before any product feature is built. This feature scaffolds a Next.js (App Router) + TypeScript + Tailwind application, installs the agreed runtime and development dependencies, defines the npm scripts, documents environment variable names, and configures `.gitignore`. The repository already contains a partially scaffolded Next.js app (`src/app`, `package.json`, `.env.example`, `.gitignore`, ESLint and TypeScript configuration). This feature reconciles that existing state with the requirements below instead of recreating it. No product features are in scope.

`AGENTS.md` states that the installed Next.js version has breaking changes relative to common knowledge. Scaffold work therefore consults the documentation in `node_modules/next/dist/docs/` before configuration or code is written.

## Glossary

- **Scaffold**: The set of configuration files, dependency declarations, scripts, and placeholder app files that make up the project foundation.
- **App**: The Next.js application in the repository root, using the App Router under `src/app`.
- **Package_Manifest**: The `package.json` file in the repository root.
- **Env_Template**: The `.env.example` file in the repository root.
- **Ignore_File**: The `.gitignore` file in the repository root.
- **Kiro_Directory**: The `.kiro` directory in the repository root, containing specs and other Kiro configuration.
- **License_File**: The `LICENSE` file in the repository root.
- **Product_Feature**: Any user-facing behavior specific to Repo Graveyard, including authentication flows, GitHub data fetching, LLM calls, revival plans, API routes, and data models.
- **Next_Docs**: The Next.js documentation in `node_modules/next/dist/docs/`.
- **Runtime_Dependencies**: `next-auth` (Auth.js), `octokit`, `zod`, and `framer-motion`, together with `next`, `react`, and `react-dom`.
- **Dev_Dependencies**: `typescript`, `tailwindcss`, `vitest`, `fast-check`, `@playwright/test`, and `prettier`, together with the ESLint and type packages the App needs.

## Requirements

### Requirement 1: Next.js App Router base

**User Story:** As a developer, I want a Next.js App Router project with TypeScript and Tailwind, so that I have a working base to build on.

#### Acceptance Criteria

1. THE Scaffold SHALL provide an App that uses the Next.js App Router with source files under `src/app`.
2. THE Scaffold SHALL set `"strict": true` in the App's TypeScript configuration.
3. THE Scaffold SHALL configure Tailwind CSS so that a Tailwind utility class applied to an element in the home page (for example, a text color or padding class) changes that element's computed style in the rendered page.
4. WHEN a client requests the root path `/` from the running App, THE App SHALL render the root layout and home page and return a successful response with no errors written to the server console or the browser console.
5. WHEN the `build` script runs on a clean checkout with dependencies installed, THE App SHALL build with exit code 0 and with zero TypeScript type errors.
6. IF the `build` script fails, THEN THE App SHALL exit with a non-zero exit code and write an error message identifying the failing file or step to standard error.
7. WHEN the `lint` script runs on a clean checkout with dependencies installed, THE App SHALL complete with exit code 0 and zero lint errors.

### Requirement 2: Follow installed Next.js conventions

**User Story:** As a developer, I want the scaffold to follow the installed Next.js version's conventions, so that breaking changes do not cause errors.

#### Acceptance Criteria

1. WHEN a Next.js configuration file or an App Router file (such as `next.config.ts`, `layout.tsx`, or `page.tsx`) is created or modified, THE Scaffold SHALL base the change on the guide or guides in Next_Docs (`node_modules/next/dist/docs/`) that cover the feature being changed, and SHALL read those guides before the change is made.
2. IF a convention in Next_Docs differs from a default generated by an earlier tool or template, THEN THE Scaffold SHALL follow the convention in Next_Docs and SHALL replace the differing default in the affected file.
3. IF no guide in Next_Docs covers the feature being created or modified, THEN THE Scaffold SHALL keep the existing file content for that feature unchanged and SHALL report the missing guide in the task output.
4. IF Next_Docs contains a deprecation notice for an API, convention, or file structure used in the Scaffold, THEN THE Scaffold SHALL use the replacement named in the notice, and SHALL contain zero references to the deprecated item in files it creates or modifies.
5. THE Scaffold SHALL retain the `AGENTS.md` file at the repository root with content byte-identical to its content before the Scaffold work began.

### Requirement 3: Runtime dependencies

**User Story:** As a developer, I want the agreed runtime dependencies installed, so that later features can use them without further setup.

#### Acceptance Criteria

1. THE Package_Manifest SHALL declare `next-auth`, `octokit`, `zod`, and `framer-motion` under `dependencies`, each with a non-empty version specifier, and SHALL NOT declare any of them under `devDependencies`.
2. THE Package_Manifest SHALL declare `next`, `react`, and `react-dom` under `dependencies`, each with a non-empty version specifier, and SHALL NOT declare any of them under `devDependencies`.
3. THE Package_Manifest SHALL declare version specifiers for which each declared package resolves to exactly one installed version, and that version SHALL satisfy the peer dependency ranges that every other declared package states for it, including `react` and `react-dom` at the same major version as each other and within the range required by the installed `next`.
4. WHEN `npm install` runs without the `--force` or `--legacy-peer-deps` flags on a clean checkout with no `node_modules` directory, THE Scaffold SHALL complete with exit code 0, SHALL print no `ERESOLVE` error, and SHALL install all packages declared under `dependencies`.
5. WHEN `npm ls` runs after a successful `npm install`, THE Scaffold SHALL exit with code 0 and report no `invalid` or `missing` packages among the dependencies named in criteria 1 and 2.
6. THE Scaffold SHALL include a `package-lock.json` that records a resolved version for each dependency named in criteria 1 and 2.

### Requirement 4: Development tooling

**User Story:** As a developer, I want the agreed development tooling installed, so that I can test, format, and lint code from the first feature.

#### Acceptance Criteria

1. THE Package_Manifest SHALL declare `vitest`, `fast-check`, `@playwright/test`, and `prettier` under `devDependencies`, each with a non-empty version range.
2. THE Package_Manifest SHALL declare `typescript`, `tailwindcss`, `eslint`, and `eslint-config-next` under `devDependencies`, each with a non-empty version range.
3. THE Scaffold SHALL provide a Vitest configuration that discovers unit test files matching `*.test.ts` and `*.test.tsx` under the `src` directory and excludes the Playwright end-to-end test directory.
4. THE Scaffold SHALL provide a Playwright configuration that discovers end-to-end test files only in a dedicated `e2e` directory, separate from the directories searched by Vitest.
5. THE Scaffold SHALL provide a Prettier configuration file that Prettier loads without error when run with the `--check` option.
6. WHEN the `test` script runs and no test files exist, THE Scaffold SHALL exit with code 0 within 30 seconds.
7. IF a Vitest test file exists and an assertion in it fails, THEN THE Scaffold SHALL exit the `test` script with a non-zero exit code and print the name of the failing test.
8. WHEN the `lint` script runs on the unmodified scaffold, THE Scaffold SHALL exit with code 0 and report zero ESLint errors.

### Requirement 5: npm scripts

**User Story:** As a developer, I want standard npm scripts, so that I can run common tasks with one command each.

#### Acceptance Criteria

1. THE Package_Manifest SHALL define a `dev` script whose command is `next dev`.
2. THE Package_Manifest SHALL define a `build` script whose command is `next build`.
3. THE Package_Manifest SHALL define a `lint` script whose command invokes ESLint.
4. THE Package_Manifest SHALL define a `typecheck` script whose command is `tsc --noEmit`.
5. THE Package_Manifest SHALL define a `test` script whose command is `vitest run`.
6. THE Package_Manifest SHALL define an `e2e` script whose command is `playwright test`.
7. WHEN `npm run lint` is executed on the Scaffold, THE Scaffold SHALL complete with exit code 0 and report 0 ESLint errors.
8. WHEN `npm run typecheck` is executed on the Scaffold, THE Scaffold SHALL complete with exit code 0 and report 0 TypeScript errors.
9. WHEN `npm run build` is executed on the Scaffold, THE Scaffold SHALL complete with exit code 0 and produce a production build output.
10. IF a script defined in criteria 1 to 6 exits with a non-zero code, THEN THE Package_Manifest SHALL cause `npm run <script>` to exit with that same non-zero code and print the failure output to the terminal.

### Requirement 6: Environment template

**User Story:** As a developer, I want a template listing the required environment variables, so that I know what to configure without exposing secrets.

#### Acceptance Criteria

1. THE Env_Template SHALL list the variable names `GITHUB_ID`, `GITHUB_SECRET`, `AUTH_SECRET`, `LLM_API_KEY`, and `GITHUB_DEMO_TOKEN`, with each name on its own line in the form `NAME=`.
2. THE Env_Template SHALL assign an empty value (zero characters after the `=`) to each listed variable.
3. THE Env_Template SHALL contain no variable names other than the five listed in criterion 1.
4. THE Env_Template SHALL contain no secret values, tokens, or credentials of any kind, including values copied from the developer's local environment file.
5. THE Scaffold SHALL keep the Env_Template tracked by Git, so that `git ls-files` lists it and `git check-ignore` reports it as not ignored.
6. THE Scaffold SHALL exclude the local environment file containing real secret values from Git tracking, so that `git check-ignore` reports it as ignored.

### Requirement 7: Git ignore rules

**User Story:** As a developer, I want a correct ignore file, so that secrets and dependencies stay out of Git while Kiro specs remain tracked.

#### Acceptance Criteria

1. THE Ignore_File SHALL cause `git check-ignore` to report `node_modules` and every path beneath it as ignored.
2. THE Ignore_File SHALL cause `git check-ignore` to report as ignored every file at the repository root whose name begins with `.env`, including `.env.local`, `.env.production`, and `.env.development.local`, except `.env.example`.
3. THE Ignore_File SHALL cause `git check-ignore` to report `.env.example` as not ignored.
4. THE Ignore_File SHALL cause `git check-ignore` to report the Kiro_Directory and every file and subdirectory within it as not ignored.
5. THE Ignore_File SHALL cause `git check-ignore` to report as ignored each of the following: `.next`, `out`, `coverage`, `playwright-report`, and `test-results`, and every path beneath each of them.
6. WHEN `git check-ignore` is run for `.kiro/specs/project-scaffold/requirements.md`, THE Ignore_File SHALL cause the command to report the path as not ignored, with exit code 1.
7. WHEN `git check-ignore` is run for `.env.local`, THE Ignore_File SHALL cause the command to report the path as ignored, with exit code 0.
8. IF a file under the Kiro_Directory has a name that matches another ignore rule in the Ignore_File (for example, a file whose name begins with `.env`), THEN THE Ignore_File SHALL still cause `git check-ignore` to report that file as not ignored.

### Requirement 8: License preservation

**User Story:** As the project owner, I want the license preserved, so that the repository's licensing is not altered by scaffolding.

#### Acceptance Criteria

1. WHEN the Scaffold is applied to a repository that contains a License_File, THE Scaffold SHALL leave the License_File byte-for-byte identical to its state before the Scaffold was applied, including content, file name, file location, and line endings.
2. IF the Scaffold would overwrite, rename, move, or delete the License_File, THEN THE Scaffold SHALL abort that operation, leave the License_File unchanged, and report the conflict to the user.
3. IF the License_File does not exist in the repository, THEN THE Scaffold SHALL not create a License_File and SHALL report the absence to the user in the Scaffold's completion output.
4. WHEN the Scaffold finishes, THE Scaffold SHALL report to the user whether the License_File was found and left unchanged, or was absent.

### Requirement 9: No product features

**User Story:** As the project owner, I want the scaffold to contain no product behavior, so that features are built later under their own specs.

#### Acceptance Criteria

1. THE Scaffold SHALL contain zero source files under `src/` that implement a Product_Feature.
2. WHEN a user requests the home page, THE Scaffold SHALL render a placeholder that displays the project name "Repo-Graveyard" as text and contains zero interactive elements (buttons, links, form controls, and elements with event handlers) and zero client-side state hooks.
3. THE Scaffold SHALL contain zero API route files and zero Auth.js route handler or provider configuration files.
4. THE Scaffold SHALL contain zero source files under `src/` that import `next-auth`, `octokit`, `zod`, or `framer-motion`.
5. IF the Package_Manifest declares a dependency that is not in the Runtime_Dependencies or Dev_Dependencies sets, THEN THE Scaffold SHALL list each such dependency by name in a report to the user and SHALL leave the Package_Manifest unchanged until the user chooses to keep or remove it.
6. IF a request is made to any path other than the home page, THEN THE Scaffold SHALL return a not-found response and SHALL NOT serve product content.
